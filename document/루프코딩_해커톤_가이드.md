## 0. 먼저, 다들 이런 의문이 들 거예요

본격적으로 들어가기 전에, 이 가이드를 준비하면서 예상되는 의문 세 가지(+추가 의문들)에 먼저 답하고 시작하겠습니다.

### 의문 1. "루프코딩을 해커톤에 어떻게 접목시키지?"

해커톤은 결국 **"짧은 시간 안에 동작하는 결과물을 여러 개의 작은 작업으로 쪼개서 완성하는 것"**입니다. 루프코딩은 정확히 "작업 하나 → 완료 기준 확인 → 다음 작업"을 반복하는 도구고요. 그래서 접목 방법은 단순합니다.

> **해커톤 = 큰 목표를 작은 "체크 가능한 작업 단위"로 쪼개고, 그 각각을 루프에 맡기는 것**

예를 들어 "채팅 앱을 만든다"는 목표를 그대로 AI에게 던지면 안 되고, "로그인 API 구현 + 테스트 통과", "메시지 전송 API 구현 + 테스트 통과", "프론트 채팅 화면 구현 + 화면에 메시지가 보임" 처럼 **독립적으로 검증 가능한 작업**으로 쪼갠 다음, 각 작업을 하나씩(혹은 팀원별로 동시에) 루프를 돌려서 처리하는 거예요.

### 의문 2. "루프코딩은 실험/파일 정리/논문 재현에 어울리는 거 아닌가요? 해커톤처럼 새로운 걸 빨리 만드는 데도 효과적인가요?"

아주 좋은 의문이고, 절반은 맞습니다. **루프코딩이 잘 먹히는 조건**은 "이것이 성공인지 실패인지를 기계적으로 판단할 수 있는가"입니다. 논문 재현이나 데이터 정리가 루프코딩에 잘 맞는 이유는 "원본과 결과가 일치하는가", "테스트가 통과하는가"처럼 판단 기준이 명확하기 때문이었죠.

그런데 사실 **해커톤 작업의 상당수도 이 조건을 만족합니다.**

- API 엔드포인트 구현 → "요청을 보내면 정해진 응답이 오는가"로 검증 가능
- 프론트 컴포넌트 구현 → "화면에 원하는 요소가 렌더링되는가"로 검증 가능
- DB 스키마/CRUD → "데이터가 저장되고 조회되는가"로 검증 가능
- 반복적인 보일러플레이트 코드 → 애초에 사람이 직접 칠 필요가 없음

실제로 Ralph 루프 기법을 만든 Geoffrey Huntley는 YC(Y Combinator) 해커톤에서 하룻밤 사이에 6개의 저장소를 만들었고, 원래 5만 달러(약 7천만 원) 규모로 예상됐던 프로젝트를 297달러의 API 비용으로 완료한 사례가 있습니다. 즉 **해커톤이야말로 시간이 없고 반복적인 코딩이 많은, 루프코딩이 가장 빛나는 환경** 중 하나입니다.

다만 반대로, **루프코딩에 안 맞는 부분**도 분명 있습니다.

- 어떤 기능을 만들지 정하는 아이디어 회의
- UX/디자인 방향 결정 (사람마다 취향이 다르고 "정답"이 없음)
- 발표 스토리텔링, 심사위원 설득 포인트 정하기
- 여러 대안 중 무엇을 선택할지 판단하는 것

**정리하면**: 해커톤을 "판단이 필요한 부분(사람이 함)"과 "구현하고 검증 가능한 부분(루프가 함)"으로 나누고, 후자를 최대한 루프에 맡겨서 시간을 버는 것이 핵심 전략입니다. 루프코딩은 아이디어를 대신 내주는 도구가 아니라, **아이디어가 정해진 뒤의 구현 속도를 극대화하는 도구**입니다.

### 의문 3. "4인이 각자 루프를 돌리면, 나중에 합칠 때 더 어려워지지 않나요?"

이것도 실제로 많이 발생하는 문제입니다. 각자 루프를 돌리면 AI가 **"국소적으로는 합리적이지만 전체적으로는 안 맞는" 결정**을 내리기 쉽습니다. 예를 들어 한 사람의 루프는 버튼 id를 `quick-add-inline`이라고 짓고, 다른 사람의 루프(혹은 그 사람이 만든 테스트)는 `inline-quick-add`를 찾는 식으로 이름이 어긋나서 통합할 때 다 깨지는 경우가 실제 사례로 보고되어 있습니다.

**해결책은 "병합을 나중에 잘하기"가 아니라 "애초에 충돌이 안 나게 미리 약속하기"입니다.** 구체적인 방법은 아래 2장에서 자세히 다룹니다. 핵심만 먼저 말하면:

1. 루프를 돌리기 **전에** 팀 전체가 공유할 "계약서"(API 형식, 변수명, 폴더 구조 등)를 먼저 문서로 정하고
2. 각자 **격리된 작업 공간**(git worktree)에서 독립적으로 루프를 돌리고
3. 중간중간 **자주, 작게** 병합하고
4. 병합 후엔 **자동 검증**(테스트)으로 어긋난 부분을 바로 잡아냅니다

### 추가로 나올 수 있는 의문들

**Q. 루프를 계속 돌리면 API 비용이나 시간이 너무 많이 들지 않나요?**
→ 반복 횟수 제한(예: 최대 10~15회)을 미리 걸어두고, 간단한 작업엔 적은 횟수, 복잡한 작업엔 많은 횟수를 배정하세요. "안 되면 멈추고 사람한테 보고"하는 탈출 조건이 필수입니다. (기본 가이드 5장 참고)

**Q. 해커톤 중간에 요구사항이 바뀌면 루프는 어떻게 하나요?**
→ 루프가 참고하는 "작업 목록 파일"(예: `PLAN.md`)을 팀 공용 파일로 두고, 요구사항이 바뀌면 그 파일부터 수정한 뒤 루프를 다시 시작하세요. 루프 안의 AI에게 직접 말로 설득하는 것보다, 파일을 고쳐서 "다음에 읽을 사양 자체"를 바꾸는 게 훨씬 안정적입니다.

**Q. AI가 "다 됐습니다"라고 했는데 실제로는 안 되면 어떡하죠? 발표 직전에 이런 게 터지면 큰일인데요.**
→ 이게 가장 중요한 포인트입니다. **팀원 개인의 "완료 보고"를 그대로 믿지 말고**, 병합 후 반드시 팀 전체가 "실제로 실행해서 눈으로 확인하는 통합 검증 단계"를 거치세요. 발표 1~2시간 전에는 반드시 처음부터 끝까지 시연 리허설을 해봐야 합니다.

**Q. 저희 팀은 다 신입인데, 세팅부터 막막해요.**
→ 아래 3장에 당일 타임라인과 준비물 체크리스트를 정리해뒀습니다. 대회 전날 미리 한 번 연습해보는 걸 강력 추천합니다.

## 1. 해커톤형 루프코딩의 기본 사이클: "Plan → Build → Repeat"

Ralph 루프 기법은 다음 3단계를 반복합니다. 이걸 팀 전체의 작업 흐름으로 그대로 가져오면 됩니다.

1. **Plan (계획)**: 지금까지 만든 코드와 목표(기획서)를 비교해서, 우선순위가 매겨진 할 일 목록을 `PLAN.md` 같은 파일로 정리
2. **Build (실행)**: 목록에서 작업 하나를 골라서 → 구현 → 테스트 → 커밋까지 하고 그 반복(iteration)을 종료
3. **Repeat (반복)**: 완전히 새로운 대화(컨텍스트)로 루프를 다시 시작해서 다음 작업을 진행

중요한 건 **③번, 매번 "새로 시작"한다는 점**입니다. 대화가 길어질수록 AI는 예전 실수나 헷갈린 정보를 계속 끌고 가면서 성능이 떨어지는데, 매 작업마다 깨끗한 상태로 다시 시작하면 이 문제를 피할 수 있습니다. 해커톤처럼 여러 작업을 빠르게 쳐내야 할 때 특히 중요한 원칙입니다.

## 2. 4인 팀 병렬 루프코딩 실전 세팅

### 2-1. 시작 전: 역할 분담 & 작업 쪼개기 (30분)

대회 시작하자마자 코드부터 짜지 말고, 먼저 이걸 정하세요.

1. 만들 것의 전체 그림을 한 문장으로 정의 (예: "OO을 할 수 있는 웹 앱")
2. 그 안에서 **독립적으로 개발 가능한 덩어리**로 쪼개기 (예: 백엔드 API / 프론트 화면 / 데이터·모델 / 배포·발표자료)
3. 팀원 4명이 덩어리 하나씩 담당 (예: 장연수-백엔드, 지수-프론트, 유리-데이터, 정경-통합/발표 등 팀 상황에 맞게)
4. **가장 먼저, 담당을 나누기 전에 아래 "공유 계약"부터 함께 정하기** (순서 중요!)

### 2-2. 공유 계약(Shared Contract) 먼저 정하기 — 병합 지옥을 막는 핵심

각자 루프를 돌리기 전에, 팀 전체가 합의해서 문서 하나에 아래 내용을 딱 박아두세요. 이 문서는 **모든 팀원의 루프 프롬프트에 그대로 포함**시킵니다.

```markdown
# CONTRACT.md (팀 전체 공유 계약)

## API 규칙
- 모든 API 응답 형식: { "success": bool, "data": ..., "error": string|null }
- 인증 토큰 헤더명: Authorization: Bearer {token}

## 이름 규칙
- 변수/함수: camelCase, 파일명: kebab-case
- 컴포넌트 id 예시: "chat-input", "chat-send-button" (실제 화면에 존재하는 요소만 여기에 등록)

## 폴더 구조
- /backend, /frontend, /shared 로 고정. 각자 자기 폴더 밖은 건드리지 않음

## 절대 하지 말 것 (Do NOT)
- 다른 사람 폴더의 파일을 직접 수정하지 않는다
- 테스트를 skip 처리해서 통과시키지 않는다
- 이 문서에 없는 새 API 응답 형식을 임의로 만들지 않는다
```

포인트는 이 계약을 **한 명(예: 통합 담당)만 수정 권한을 갖게** 하고, 나머지는 이 문서를 "읽기 전용 사양"으로 취급하는 것입니다. 다들 각자 편한 대로 이름을 짓다 보면 반드시 어긋납니다.

### 2-3. Git Worktree로 물리적으로 작업 공간 분리하기

같은 저장소 안에서 4명이 동시에 파일을 건드리면 매번 충돌이 납니다. `git worktree`를 쓰면 **같은 저장소, 다른 폴더**에서 각자 독립적으로 작업할 수 있습니다.

```bash
# 팀 리포지토리 기준으로, 각자 자기 브랜치의 작업 폴더를 만든다
git worktree add ../team-backend -b feature/backend main
git worktree add ../team-frontend -b feature/frontend main
git worktree add ../team-data -b feature/data main

# 이제 각자 자기 폴더에서 작업 (예: 장연수는 ../team-backend 폴더에서 루프 실행)
cd ../team-backend
```

이렇게 하면 각자 자기 폴더에서 마음껏 루프를 돌려도 서로 파일을 덮어쓸 일이 없고, git 브랜치를 통해서만 서로의 작업이 연결됩니다. 다만 주의할 점이 두 가지 있습니다.

- **`git stash`는 워크트리 간에 공유되니 쓰지 말고, 그때그때 바로 커밋**하는 습관을 들이세요.
- 각 폴더마다 `node_modules` 설치, 실행 포트를 따로 잡아야 할 수 있으니(예: 백엔드는 3001, 프론트는 3000) 미리 정해두세요.

### 2-4. 각자 자기 파트의 PLAN.md 만들고 루프 시작

각 팀원은 자기 폴더 안에 자기 파트의 할 일 목록(`PLAN.md`)을 만들고 위에서 정한 `CONTRACT.md`를 참고해서 루프를 시작합니다. 프롬프트 예시는 4장 참고.

### 2-5. 자주, 작게 통합하기 (2시간마다 추천)

하루 끝에 한 번에 다 합치려고 하면 충돌이 산더미처럼 쌓입니다. **2시간에 한 번씩** 통합 담당자(또는 돌아가면서)가 아래처럼 병합을 시도하세요.

```bash
cd ../integration   # 통합용 워크트리
git merge feature/backend
git merge feature/frontend
git merge feature/data
```

병합 후에는 반드시 **실제로 실행**해서 눈으로 확인하고, 자동화된 테스트가 있다면 돌려봅니다. 이 단계에서 발견되는 이름/형식 불일치는 대부분 "계약 문서를 안 지켜서" 생기는 것이니, 발견 즉시 계약 문서에 명시하고 전체 공지하세요.

### 2-6. 최종 통합 검증 (발표 전 필수)

발표 1~2시간 전에는 새 기능 추가를 멈추고, 아래를 팀 전체가 함께 확인하는 "통합 검증 루프"를 한 번 돌리세요.

- 처음부터 끝까지 실제 시나리오대로 실행해서 확인 (배포/실행 환경에서!)
- 테스트가 있다면 전체 테스트 스위트 실행
- 발표에서 보여줄 화면/기능을 리허설 순서대로 미리 눌러보기

이 단계를 건너뛰고 "루프가 다 됐다고 했으니 되겠지"라고 믿었다가 발표 중에 안 되는 경우가 제일 아쉬운 실패 사례입니다.

| 13:15 ~ 15:00 | 2차 루프 구현 | 남은 기능, 발견된 버그 수정 루프 |
| 15:00 ~ 15:20 | 2차 통합 | 병합 + 테스트 |
| 15:20 ~ 16:20 | 마무리 & 다듬기 | UI 다듬기, 예외 처리, 발표 자료 준비 (이 구간은 사람 판단 위주) |
| 16:20 ~ 16:50 | **최종 통합 검증** | 전체 시나리오 리허설 (2-6 참고) — 새 기능 추가 금지! |
| 16:50 ~ 17:00 | 발표 준비 | 시연 순서 최종 확인 |

> 점심시간은 팀 상황에 맞게 넣으세요. 핵심은 **"통합은 하루 끝에 한 번이 아니라 최소 2번 이상, 그리고 마지막엔 반드시 새 기능 추가를 멈추는 구간을 확보"**하는 것입니다.

## 4. 바로 쓰는 예시 프롬프트

### 공유 계약(CONTRACT.md) 작성용 — 팀 전체가 같이 볼 때

```
우리 팀이 만들 [프로젝트 설명]에 대해, 4명이 각자 백엔드/프론트/데이터/통합을 나눠서
동시에 개발할 예정이야. 각자 루프를 돌리기 전에 팀 전체가 지킬 CONTRACT.md를 만들어줘.
포함할 내용: API 응답 형식, 인증 방식, 변수/파일 이름 규칙, 폴더 구조, 그리고
"절대 하지 말 것" 목록(다른 사람 폴더 수정 금지, 테스트 skip 금지 등).
아직 화면에 존재하지 않는 요소의 id는 상상해서 넣지 말고, 실제로 만들 것만 적어줘.
```

### 개별 파트 루프 시작용 (예: 백엔드 담당)

```
아래 CONTRACT.md 내용을 반드시 지키면서 [담당 파트, 예: 백엔드 API]를 구현해줘.
[CONTRACT.md 내용 붙여넣기]

목표: [구체적 기능 목록, 예: 로그인/회원가입/메시지 전송 API]
성공 기준: 각 API를 [테스트 방법, 예: curl 또는 테스트 코드]로 호출했을 때
CONTRACT.md에 정의된 응답 형식대로 정상 동작해야 해.

작업 순서: 할 일 목록을 PLAN.md에 우선순위대로 정리 → 하나씩 구현 → 직접 실행해서 확인 →
커밋 → 다음 항목으로. 다른 팀원의 폴더(frontend, data)는 절대 건드리지 마.
막히면 최대 10번까지 시도해보고, 안 되면 멈추고 어떤 문제인지 정리해서 보고해줘.
```

### 통합/병합 검증용 (통합 담당자용)

```
지금 feature/backend, feature/frontend, feature/data 브랜치를 병합하려고 해.
병합 후 아래를 확인해줘:
1. CONTRACT.md에 정의된 이름/형식과 실제 코드가 일치하는지 (다르면 어디가 다른지 구체적으로)
2. 병합 후 전체를 실행했을 때 에러 없이 켜지는지
3. 테스트가 있다면 전부 실행해서 통과하는지, skip된 테스트는 없는지
문제를 발견하면 직접 고치지 말고, 어떤 파일에서 무엇이 어긋났는지 먼저 정리해서 보여줘.
```

### 최종 시연 리허설 전 점검용

```
발표 시연에서 보여줄 시나리오는 [시나리오 단계별로 나열]이야.
이 순서대로 처음부터 끝까지 실제로 실행해보고, 각 단계에서 예상과 다른 부분이 있으면
전부 정리해서 알려줘. 지금 단계에서는 새로운 기능을 추가하지 말고, 있는 걸 검증만 해줘.
```

## 5. 마무리 체크리스트

- [ ] 코드를 짜기 전에, "판단이 필요한 부분"과 "루프에 맡길 부분"을 나눴는가?
- [ ] 루프를 돌리기 전에 팀 전체가 `CONTRACT.md`(공유 계약)에 합의했는가?
- [ ] `git worktree`로 각자의 작업 공간을 물리적으로 분리했는가?
- [ ] 하루 끝에 한 번이 아니라, 중간중간 자주 병합하기로 계획했는가?
- [ ] 발표 전 "새 기능 추가 금지 + 전체 리허설" 구간을 일정에 확보했는가?
- [ ] 각 루프에 최대 시도 횟수(탈출 조건)를 걸어뒀는가?

이 체크리스트만 지켜도 "각자 열심히 루프 돌렸는데 합치니까 아무것도 안 된다"는 최악의 시나리오는 충분히 피할 수 있습니다. 화이팅입니다!
