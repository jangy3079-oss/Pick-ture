# 루프코딩(Loop Coding / Loop Engineering) 완전 초보자 가이드

> 이 문서는 루프코딩을 처음 접해보는 분들을 위해 작성되었습니다.
> "AI한테 코드 좀 짜달라고 했는데 자꾸 이상하게 나와요" 하는 분들을 위한 문서예요.
> 어려운 용어 없이, 예시 위주로 설명합니다.

---

## 1. 이 문서를 왜 읽어야 하나요?

요즘 연구실에서 Claude, ChatGPT, Claude Code, Cursor 같은 AI 코딩 도구를 안 쓰는 사람이 거의 없죠.
그런데 많은 신입 연구생들이 이렇게 씁니다.

> "이 코드 짜줘" → 결과가 이상함 → "아니 이거 말고 이렇게 해줘" → 또 이상함 → 좌절, 포기, 그냥 내가 짬

이렇게 **매번 사람이 일일이 지시하고, 결과를 보고, 또 지시하는 방식**을 "프롬프트 방식"이라고 부릅니다.

이 문서에서 배울 **"루프코딩(루프 엔지니어링)"**은 이것과 다릅니다. 사람이 매번 개입하는 대신, **"이 목표를 달성할 때까지 스스로 시도하고, 확인하고, 고쳐라"** 라고 시스템을 짜두는 방식입니다. 이걸 잘 알아두면 앞으로 연구실에서 코드 작업, 데이터 처리, 논문 관련 작업을 할 때 훨씬 적은 노력으로 훨씬 좋은 결과를 얻을 수 있습니다.

## 2. 루프코딩이 뭔가요? (비유로 이해하기)

### 비유: 요리를 시킬 때

**기존 방식 (프롬프트 방식)**을 요리에 비유하면:

> 나: "국 좀 끓여줘"
> AI: (끓임) "다 됐어요"
> 나: (맛보고) "너무 짜네, 물 좀 더 넣어줘"
> AI: (물 넣음) "다 됐어요"
> 나: (또 맛보고) "이제 싱거워, 소금 좀 더"
> ... (무한 반복, 내가 계속 옆에서 맛을 봐야 함)

**루프코딩 방식**은:

> 나: "이 국이 '적당히 간이 맞다'는 기준을 만족할 때까지, 네가 직접 맛을 보면서 간을 맞춰봐. 소금/물 조절 다 네가 판단해서 하고, 다 되면 나한테 알려줘."
> AI: (스스로 맛보고 → 짜다고 판단 → 물 추가 → 다시 맛보고 → 아직 부족 → 소금 살짝 → 다시 확인 → 완성) "다 됐습니다, 확인해보세요"

차이가 보이시나요? 루프코딩에서는 **"완료 기준"**과 **"스스로 확인할 수단"**을 미리 딱 정해주고, 그 다음부터는 AI가 스스로 (시도 → 결과 확인 → 문제 있으면 수정 → 다시 시도)를 반복합니다. 이 반복 사이클을 "루프(loop)"라고 부르는 거예요.

### 조금 더 정확한 정의

> **루프코딩** = AI 코딩 에이전트에게 "무엇을 해라"가 아니라 "어떤 상태가 될 때까지 스스로 반복하며 작업해라"라고 맡기는 개발 방식.
> 에이전트는 **계획(Plan) → 실행(Act) → 관찰(Observe) → 수정(Revise)** 을 목표가 달성될 때까지 스스로 반복합니다.

참고로 프로그래밍에서 배우는 `for`, `while` 반복문과는 다른 개념입니다. 그건 "코드 안에서 도는 반복문"이고, 여기서 말하는 루프는 "AI 에이전트의 작업 방식 자체가 반복 구조"라는 뜻입니다. 헷갈리지 않게 주의하세요.

## 3. 기존 방식 vs 루프코딩, 한눈에 비교

| 구분 | 기존 프롬프트 방식 | 루프코딩 방식 |
|---|---|---|
| 누가 반복하나 | 사람이 매번 지시 | AI가 스스로 반복 |
| 사람의 역할 | 매 단계마다 확인하고 다음 지시를 줌 | 목표와 규칙만 정해주고 기다림 (또는 다른 일 함) |
| 실패했을 때 | 사람이 알아채고 다시 지시해야 함 | AI가 스스로 실패를 감지하고 다른 방법 시도 |
| 언제 끝나나 | 사람이 "이제 됐다" 라고 말할 때 | 미리 정한 "완료 조건"을 만족할 때 |
| 적합한 작업 | 짧고 간단한 1회성 작업, 대화하듯 다듬는 글쓰기 | 명확히 "성공/실패"를 판단할 수 있는 반복 작업 (테스트 통과, 버그 수정, 데이터 정제 등) |

## 4. 왜 연구실 작업에 특히 유용한가요?

사실 **연구 자체가 원래 루프 구조**입니다. 여러분이 이미 익숙한 예를 보면:

- 실험 설계 → 실행 → 결과 분석 → 가설 수정 → 다시 실험
- 모델 학습 → 성능 평가 → 하이퍼파라미터 조정 → 다시 학습
- 코드 작성 → 실행 → 에러 확인 → 수정 → 다시 실행

이 모든 게 "될 때까지 반복" 구조죠. 그래서 루프코딩은 특히 다음과 같은 연구실 상황에서 강력합니다.

- 코드에 버그가 있는데 정확히 어디가 문제인지 모를 때
- 여러 파일/여러 데이터셋에 대해 똑같은 작업을 반복해야 할 때
- "일단 돌아가는 것"이 아니라 "테스트를 통과하는 것"처럼 명확한 성공 기준이 있을 때
- 실험을 여러 번 돌리고 로그를 정리하는 것처럼, 사람이 옆에 계속 붙어있기 지루한 작업일 때

반대로 **루프코딩이 안 어울리는 경우**도 있습니다: 논문 초록처럼 "정답이 없고 취향/스타일이 중요한 글쓰기", 방향 자체를 아직 못 정한 탐색적 대화, 중요한 의사결정(예: "이 실험 결과를 논문에 이 방식으로 써도 될까?") 같은 것들은 AI 혼자 반복시키지 말고 사람이 계속 확인하면서 진행하는 게 맞습니다.

## 5. 루프를 이루는 5가지 핵심 요소

좋은 루프를 만들려면 아래 5가지를 반드시 챙겨야 합니다. 하나라도 빠지면 루프가 산으로 가거나, 영원히 안 끝나거나, 엉뚱한 결과를 "성공"이라고 착각합니다.

### ① 명확한 종료 조건 (가장 중요!)

"언제 끝난 건지"를 AI도 스스로 판단할 수 있게, 구체적이고 확인 가능한 형태로 줘야 합니다.

- ❌ 나쁜 예: "코드 잘 짜줘" (뭐가 "잘"인지 AI도 모름)
- ✅ 좋은 예: "`pytest` 실행했을 때 모든 테스트가 통과할 때까지"
- ✅ 좋은 예: "이 CSV 파일 100개를 전부 같은 형식으로 변환하고, 변환 후 행 개수가 원본과 일치하는지 확인될 때까지"

### ② 스스로 확인할 수 있는 도구

AI가 "내가 한 게 맞는지" 직접 확인할 방법이 있어야 합니다. 테스트 코드 실행, 스크립트 실행 결과 확인, 파일 개수 세어보기 같은 것들이죠. 이게 없으면 AI는 그냥 "다 했습니다!"라고 말만 하고 실제로는 틀렸을 수 있습니다.

### ③ 실패 시 멈추는 조건 (탈출구)

"이런 경우엔 더 이상 혼자 시도하지 말고 나한테 물어봐" 라는 조건을 꼭 걸어두세요. 안 그러면 AI가 같은 실수를 계속 반복하거나(무한 루프), 잘못된 방향으로 계속 파고들 수 있습니다.

- 예: "5번 시도해도 안 되면 멈추고 어떤 에러가 났는지 정리해서 보고해줘"

### ④ 진행 상황을 기록하는 방법

작업이 길어지면 AI도 "내가 지금까지 뭘 했는지"를 잊어버릴 수 있습니다. 중간 진행 상황을 파일로 남기게 하거나, TODO 리스트를 갱신하게 하면 훨씬 안정적으로 돌아갑니다.

### ⑤ 정말로 "다르게" 시도하는 것 (똑같은 실수 반복 금지)

같은 방법을 실패했는데 또 그대로 시도하는 건 루프가 아니라 그냥 "헛도는 것"입니다. "이전 시도에서 왜 실패했는지 분석하고, 다른 방법으로 시도해줘"라고 명시적으로 요구하는 게 중요합니다.

## 6. 좋은 루프를 설계하는 단계별 가이드라인

1. **목표를 사람의 말이 아니라 "검사 가능한 조건"으로 바꾸기**
   "코드 고쳐줘" → "이 함수를 실행했을 때 이 에러가 더 이상 안 나올 때까지, 그리고 기존 테스트 3개가 계속 통과하는 상태로"

2. **AI가 스스로 확인할 방법을 함께 알려주기**
   테스트 파일 위치, 실행 명령어, 기대하는 출력 형태 등을 구체적으로 알려주세요.

3. **최대 시도 횟수 / 멈춰야 할 조건을 정하기**
   "3번 시도해도 안 풀리면 멈추고 상황 요약해줘" 처럼 안전장치를 겁니다.

4. **작게 시작해서 점점 범위를 넓히기**
   처음부터 "전체 프로젝트 다 고쳐줘"보다는 파일 하나, 함수 하나로 시작해서 루프가 잘 도는지 확인 후 범위를 넓히세요.

5. **결과를 반드시 사람이 검토하기**
   루프가 "완료됐다"고 보고해도, 특히 연구/논문에 쓰일 결과라면 사람이 최종 확인은 꼭 해야 합니다. AI가 "테스트를 통과했다"고 스스로 판단한 것과, 그게 "연구적으로 올바른 결과"인지는 다른 문제입니다.

6. **처음엔 지켜보다가, 신뢰가 쌓이면 맡기는 범위를 넓히기**
   처음 몇 번은 AI가 반복하는 과정을 옆에서 지켜보고, 이상한 방향으로 가면 바로 개입하세요. 익숙해지면 점점 더 큰 작업을 맡길 수 있습니다.

## 7. 흔한 실수 (신입생이 특히 조심할 것)

- **종료 조건 없이 "알아서 잘 해줘"라고만 시키기** → AI가 뭘 목표로 해야 할지 몰라서 엉뚱하게 "완료"라고 우김
- **검증 수단 없이 결과만 믿기** → "테스트 통과했어요!"라는 말만 믿고 안 열어봤다가 나중에 사고
- **무한 루프 방치** → 시도 횟수 제한을 안 걸어서 같은 실수를 계속 반복 (시간과 비용 낭비)
- **중요한 판단까지 루프에 맡기기** → "이 데이터 전처리 방식이 논문 방법론상 타당한가?" 같은 건 AI 혼자 반복시켜서 결정할 문제가 아님
- **한 번에 너무 큰 작업을 맡기기** → "우리 랩 전체 코드베이스 리팩토링해줘" 같은 건 처음엔 무리, 작은 단위로 쪼개서 시작

## 8. 실전 예제 시나리오

### 예제 1: 코드에 원인 모를 버그가 있을 때

**상황**: 데이터 전처리 스크립트를 돌렸는데 특정 데이터에서만 에러가 남. 원인을 못 찾겠음.

**루프 설계**:
- 종료 조건: 에러 없이 전체 데이터셋이 끝까지 처리됨
- 확인 수단: 스크립트를 실제로 실행해서 에러 로그 확인
- 탈출 조건: 5번 시도 후에도 실패하면 멈추고 에러 원인 후보들을 정리해서 보고

### 예제 2: 여러 실험을 반복 실행하고 정리해야 할 때

**상황**: 하이퍼파라미터 조합 10개에 대해 각각 모델을 학습시키고 결과를 표로 정리해야 함.

**루프 설계**:
- 종료 조건: 10개 조합 전부에 대한 결과가 표(CSV/마크다운)에 정리됨
- 확인 수단: 각 실행이 끝날 때마다 결과 파일이 생성됐는지, 값이 비어있지 않은지 확인
- 탈출 조건: 특정 조합에서 학습이 계속 실패하면 그 조합만 표시해두고 나머지는 계속 진행

### 예제 3: 논문 코드(재현) 실행이 안 될 때

**상황**: GitHub에서 논문 공식 코드를 받아왔는데 환경 설정부터 실행까지 에러투성이.

**루프 설계**:
- 종료 조건: README에 나온 예시 명령어가 에러 없이 끝까지 실행되고, 예시 결과와 비슷한 출력이 나옴
- 확인 수단: 실제로 명령어를 실행해보고 로그 확인
- 탈출 조건: 라이브러리 버전 충돌처럼 근본적인 문제면, 무작정 계속 시도하지 말고 어떤 문제인지 정리해서 보고

## 9. 바로 써먹는 예시 프롬프트 모음

아래 프롬프트들은 그대로 복사해서 상황에 맞게 괄호 안만 바꿔 쓰면 됩니다. 핵심은 항상 **"목표(종료 조건) + 확인 방법 + 멈출 조건"** 세 가지를 넣는 것입니다.

### 버그 수정용

```
[파일/함수 이름]에서 [증상, 예: IndexError가 발생]하는 문제를 고쳐줘.
성공 기준: [실행 명령어]를 실행했을 때 에러 없이 끝까지 실행되고, 결과가 [기대하는 형태]와 같아야 해.
방법: 코드를 고친 후 직접 실행해서 결과를 확인하고, 안 되면 원인을 다시 분석해서 다른 방법으로 시도해줘.
최대 5번까지 시도해보고, 그래도 안 되면 멈추고 어떤 시도를 했고 왜 실패했는지 정리해서 알려줘.
```

### 반복 작업(여러 파일/데이터) 자동화용

```
[폴더 경로]에 있는 파일 [개수]개에 대해 전부 [작업 내용, 예: 같은 형식으로 변환]을 해줘.
성공 기준: 변환된 파일 개수가 원본 개수와 같고, 각 파일을 열었을 때 [확인할 조건]을 만족해야 해.
하나씩 처리하면서 스스로 결과를 확인하고, 실패한 파일이 있으면 목록으로 남겨줘.
전부 끝나면 처리 결과 요약(성공/실패 개수)을 알려줘.
```

### 테스트 기반 개발용

```
[기능 설명]을 구현해줘.
먼저 이 기능이 맞는지 확인할 수 있는 테스트 코드를 [테스트 케이스 예시]를 포함해서 작성하고,
그 다음 테스트를 통과하도록 실제 기능을 구현해줘.
모든 테스트가 통과할 때까지 반복하고, 통과하면 어떤 코드를 어떻게 짰는지 요약해줘.
```

### 실험 반복 실행용

```
[스크립트 이름]을 아래 조건 조합으로 각각 실행해줘: [조건 목록].
각 실행이 끝나면 결과를 [저장 형식, 예: results.csv]에 한 줄씩 추가해줘.
성공 기준: 모든 조합에 대한 결과가 빠짐없이 기록되어 있어야 해.
특정 조합에서 계속 에러가 나면, 그 조합은 실패로 표시하고 나머지 조합은 계속 진행해줘.
전부 끝나면 몇 개 성공/실패했는지와 실패 원인을 요약해줘.
```

### 논문/공개 코드 재현용

```
[GitHub 링크 또는 코드 경로]의 코드를 로컬 환경에서 실행 가능하게 만들어줘.
성공 기준: README에 나온 예시 명령어가 에러 없이 실행되고, 결과가 README의 예시 결과와 비슷해야 해.
환경 설정 문제(라이브러리 버전 등)는 직접 해결을 시도하고, 시도한 내용을 기록해줘.
근본적으로 해결이 안 되는 문제(예: 더 이상 존재하지 않는 데이터셋)를 만나면 즉시 멈추고 나한테 알려줘.
```

> 💡 팁: 프롬프트 끝에 항상 "다 됐다고 하기 전에 실제로 실행/확인해보고 말해줘" 를 붙이는 습관을 들이면, AI가 확인 없이 "완료했습니다"라고 거짓 보고하는 걸 줄일 수 있습니다.

## 10. 마무리 체크리스트

작업을 AI에게 루프로 맡기기 전에 아래 4가지만 확인하세요.

- [ ] 이 작업의 "성공"을 AI도 스스로 확인할 수 있는 구체적인 기준으로 말했는가?
- [ ] AI가 결과를 직접 확인할 수 있는 수단(실행/테스트/파일 확인)을 줬는가?
- [ ] 안 될 경우 멈추고 물어볼 조건(시도 횟수, 실패 유형)을 정해줬는가?
- [ ] 결과가 나오면 내가 직접 한 번 더 확인할 계획인가? (특히 연구/논문에 쓰일 결과라면 필수)

이 네 가지만 지켜도 "AI한테 시켰는데 이상하게 나왔어요"라는 상황을 훨씬 줄일 수 있습니다. 처음엔 어색해도, 몇 번 해보면 훨씬 적은 노력으로 훨씬 많은 작업을 처리할 수 있게 됩니다.
