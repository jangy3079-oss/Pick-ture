## 1. 먼저, 핵심 원칙 한 줄 요약

> **루프는 대화를 기억하는 게 아니라, 매 반복마다 디스크(파일)를 새로 읽고 시작한다.**

3편 전체가 사실 이 한 문장에서 나옵니다. 통합 중 뭔가 문제가 생겼을 때 "누구한테 다시 말해줘야 하나, 루프를 세워야 하나"로 헷갈릴 때마다 이 원칙으로 돌아오면 답이 나옵니다. 아래는 이 원칙을 상황별로 풀어낸 실전 판단 기준입니다.

| 상황 | 루프를 세워야 하나? | 무엇을 고쳐야 하나? |
|---|---|---|
| 이름/형식이 살짝 어긋남 (예: 필드명 하나 다름) | 아니요, 다음 반복이 자동으로 반영 | `CONTRACT.md`만 명확히 고치면 됨 |
| 계약 자체는 맞는데 코드가 계약을 어김 | 아니요 | 통합 브랜치에서 고친 뒤, 그 수정을 **원래 담당자 브랜치로 반드시 되돌려주기** (2장 참고) |
| API 구조/인증 흐름처럼 근본적인 설계가 틀림 | **네, 담당자에게 바로 알려서 다음 반복 전에 확인** | `CONTRACT.md` + `PLAN.md` 둘 다 수정, 담당자와 짧게 대화 |
| 특정 작업에서 루프가 계속 같은 실패를 반복 (탈출 조건 도달) | 네, 이미 루프 스스로 멈췄을 것 | 사람이 직접 원인 파악 후 재개 |

## 2. 토큰 효율: 해커톤 예산은 무한하지 않다

### 2-1. 잠깐, 개념 복습: 바이브코딩 vs 루프코딩

1편에서 다뤘던 내용을 아주 간단히 다시 짚고 갑니다.

| 구분 | 바이브코딩 (Vibe Coding) | 루프코딩 (Loop Coding) |
|---|---|---|
| 핵심 주체 | 인간 중심 — 사람이 방향을 정하고 결과를 눈으로 확인 | AI 에이전트 중심 — AI가 스스로 검증하고 수정 |
| 작동 방식 | 프롬프트 → 코드 확인 → 사람이 다시 지시 | 코드 작성 → 테스트 실행 → 에러 분석 → 수정 (반복) |
| 적합한 작업 | UI 프로토타이핑, 짧은 스크립트 | 복잡한 백엔드 로직, 리팩토링, 반복적인 디버깅 |

한 문장으로: **바이브코딩은 사람이 매번 타이핑을 대신 시키는 것, 루프코딩은 사람이 검증 기준만 정해두고 반복 자체를 AI에게 맡기는 것**입니다.

### 2-2. 잠깐, 그냥 원샷(바이브코딩)으로 충분한 거 아니야?

실제로 요즘 해커톤에서 "루프 안 돌리고 한 번에 시켰는데도 결과가 꽤 좋던데?"라는 경험을 많이들 합니다. 이 느낌은 틀린 게 아니에요. 로그인 API, 표준 CRUD, 흔한 보일러플레이트처럼 전 세계 개발자가 이미 수도 없이 짜본 패턴은 모델이 학습 데이터에서 거의 "외우다시피" 하고 있어서, 원샷 품질 자체가 이미 높습니다. 이런 작업엔 루프가 반복해서 고칠 "실패"가 애초에 별로 없어요.

다만 두 가지는 주의하세요. 첫째, 데모에서 잘 되어 보이는 건 생존 편향일 수 있습니다 — 원샷 코드에 숨은 엣지 케이스(동시 요청, 토큰 만료, 이상한 입력값)는 짧은 시연 중엔 안 터지다가 심사위원이 직접 건드리거나 발표 중 하필 걸리면 그때 터집니다. 둘째, "원샷이 잘 되더라"는 결론이 "이 작업이 원샷으로 충분한 종류였다"이지, "루프코딩 자체가 필요 없다"는 아닙니다.

그래서 매번 루프를 돌릴지 말지 고민될 때는 아래 기준 하나만 물어보세요.

> **"내가 결과물을 눈으로 슥 보고 맞다/틀리다를 바로 판단할 수 있는가?"**
> → 판단 가능하면 원샷 + 눈으로 검토가 더 빠르고 토큰도 아낍니다 (**루프를 안 도는 게 사실 가장 확실한 토큰 절약법**입니다).
> → 실제로 실행/테스트를 해봐야만 맞는지 아는 애매한 영역이라면 루프가 유리합니다. 사람이 어차피 반복 실행하며 디버깅할 일을 AI가 대신 반복해주는 것뿐이니까요.

백엔드 기준으로 구체적으로 나누면 이렇습니다.

| 그냥 원샷으로 충분한 것 | 루프를 돌릴 가치가 있는 것 |
|---|---|
| 단일 CRUD 엔드포인트 하나 | 인증/인가 흐름 (JWT 발급·갱신·만료·권한 체크처럼 엣지케이스가 많은 로직) |
| DTO/엔티티/Repository 인터페이스 생성 | 결제, 포인트 차감, 재고 처리처럼 동시성·트랜잭션이 얽힌 로직 |
| 설정 파일(application.yml, Dockerfile) 초안 | 외부 API 연동 (소셜로그인, 결제 PG, 지도/알림 API) — 실제로 호출해봐야만 드러나는 문제가 많음 |
| 간단한 유틸 함수, 기본 유효성 검사 | 여러 엔티티에 걸친 반복 작업 (예: 엔티티 10개짜리 CRUD를 같은 패턴으로 찍어내기) |
| 널리 알려진 보일러플레이트(표준 필터, 미들웨어 뼈대) | 원인 모를 기존 버그 수정, N+1 쿼리 같은 성능 이슈 디버깅 |
| | 마이그레이션 이후 기존 코드와의 정합성 확인 |

참고로 이 대회 자체가 "루프코딩"을 주제로 하는 만큼, 심사 기준에 "언제, 어디에 루프를 썼는가"에 대한 판단력도 포함될 가능성이 높습니다. "이 부분(인증, 결제 로직)엔 루프를 썼고, 이 부분(CRUD, 설정)은 원샷으로 처리해서 시간을 아꼈다"라고 설명할 수 있으면, 무조건 루프를 다 썼다고 말하는 팀보다 오히려 더 좋은 인상을 줄 수 있습니다.

### 2-3. 그런데 왜 루프코딩이 토큰을 훨씬 많이 먹나?

| 구분 | 바이브코딩 | 루프코딩 |
|---|---|---|
| 토큰 소모 | 상대적으로 적고 통제 가능 — 사람이 필요할 때만 질문하고 컨텍스트를 직접 관리 | 극심함 — 코드 읽기 → 실행 결과 분석 → 재작성을 5~10번씩 자동 반복 |
| 비용 체감 | 사람이 매번 개입하니 자연스럽게 브레이크가 걸림 | 백그라운드에서 알아서 도니, 단일 문제 하나에 바이브코딩 대비 수 배~수십 배의 토큰이 순식간에 쓰일 수 있음 |

즉 루프코딩은 "적은 노력으로 많은 작업"이 가능한 대신, **잘못 설계하면 API 비용과 시간을 한 방향으로만 태우는** 위험이 있습니다. 해커톤처럼 예산과 시간이 뻔히 정해져 있는 환경에서는 이 부분을 반드시 관리해야 합니다.

### 2-4. 토큰 낭비를 막는 4가지 핵심 기법

성능(결과물의 질)을 타협하지 않으면서 토큰을 줄이는 핵심은 **"에이전트가 보는 컨텍스트의 범위를 얼마나 정밀하게 통제하느냐"**입니다. 특히 백엔드 API나 RAG 파이프라인처럼 파일이 많고 구조가 복잡한 프로젝트일수록 중요합니다.

**① 작업 공간을 철저히 격리하기**

프로젝트 전체를 통째로 에이전트에게 넘기면 매 반복(iteration)마다 수만 토큰이 그냥 증발합니다. 예를 들어 Spring Boot나 FastAPI로 백엔드를 만든다면, 지금 작업 중인 서비스 로직과 그것이 의존하는 DTO·엔티티 파일 정도만 명시적으로 지정해서 루프를 돌리세요. `.aiderignore` 같은 설정 파일(또는 `.gitignore`처럼 특정 폴더를 컨텍스트에서 제외하는 설정)로 빌드 결과물, 로그 파일, 지금 당장 관계없는 다른 도메인 코드가 컨텍스트에 섞여 들어가지 않게 원천 차단하는 것이 좋습니다.

**② 검증 테스트 범위를 아주 좁게 설정하기**

에이전트가 피드백을 받는 기준이 DB 쿼리부터 화면단까지 이어지는 무거운 통합 테스트(E2E)라면, 한 번 실패할 때마다 뱉어내는 에러 로그 길이만 수천 토큰에 달합니다. 대신 특정 모듈의 입출력만 검증하는 아주 작은 단위의 유닛 테스트를 먼저 짜두고, 루프가 오직 그 테스트 통과에만 집중하도록 하세요. 원인을 찾는 속도가 빨라지니 반복 횟수와 토큰이 동시에 줄어듭니다.

**③ 문서를 통째로 붙여넣지 말고, 필요할 때만 동적으로 조회하기**

공식 문서나 스키마 정보를 프롬프트에 매번 욱여넣는 대신, MCP(Model Context Protocol) 같은 도구를 연동해서 에이전트가 필요한 순간에만 특정 프레임워크 레퍼런스나 DB 스키마를 검색해서 읽어오도록 구성하세요. 기본 프롬프트는 가볍게 유지하면서도 필요할 때 정확한 정보를 가져올 수 있습니다.

**④ 최대 반복 횟수(Max Iterations)를 엄격히 제한하기**

보통 3~4번을 돌았는데도 테스트를 통과 못 한다면, 단순 오타 문제가 아니라 애초에 아키텍처 설계나 유닛 테스트 자체에 논리적 결함이 있을 확률이 높습니다. 이때는 무의미하게 토큰을 계속 태우기보다 루프를 강제 종료하고, 사람이 직접 에러를 분석해서 방향을 다시 잡아주는 것이 훨씬 경제적입니다. (1편·2편에서 강조한 "탈출 조건"과 완전히 같은 이야기입니다.)

### 2-5. 토큰을 아끼는 프롬프트 예시 (Before / After)

같은 작업이라도 프롬프트를 어떻게 짜느냐에 따라 컨텍스트 크기가 크게 달라집니다.

**예시 1 — 파일 범위 지정**

```
❌ 비효율: "우리 프로젝트 전체 구조 보고 로그인 기능 버그 좀 고쳐줘."
   → 에이전트가 관계없는 폴더까지 전부 읽어서 매 반복마다 수만 토큰 낭비

✅ 효율: "src/auth/login_service.py와 그 의존 파일인
   src/auth/dto/login_request.py, src/auth/entity/user_entity.py
   이 3개 파일만 참고해서 [증상]을 고쳐줘. 이 3개 파일 외의 폴더는 읽지 마."
```

**예시 2 — 테스트 범위 좁히기**

```
❌ 비효율: "이 API가 통합 테스트(E2E)를 통과할 때까지 반복해줘."
   → 실패할 때마다 DB~화면단 로그가 수천 토큰씩 반환됨

✅ 효율: "tests/unit/test_login_service.py 의 유닛 테스트 3개
   (정상 로그인 / 비밀번호 오류 / 존재하지 않는 유저)만 통과할 때까지 반복해줘.
   이 3개 테스트 범위 밖의 동작은 신경 쓰지 마."
```

**예시 3 — 문서 붙여넣기 대신 필요할 때만 조회**

```
❌ 비효율: "[공식 문서 전체 5,000단어를 프롬프트에 그대로 붙여넣고] 이거 참고해서 구현해줘."

✅ 효율: "Spring Data JPA의 @Query 사용법이 필요하면, 연결된 문서 도구로
   그 부분만 검색해서 확인한 뒤 구현해줘. 문서 전체를 읽을 필요는 없어."
```

**예시 4 — 반복 횟수 명시 + 실패 시 보고**

```
❌ 비효율: "테스트를 통과할 때까지 계속 반복해줘." (무제한)

✅ 효율: "최대 4번까지만 시도해줘. 4번 안에 유닛 테스트를 통과 못하면
   즉시 멈추고, 지금까지 시도한 접근과 각각 왜 실패했는지 요약해서 보고해줘.
   그건 코드 오타가 아니라 설계 자체의 문제일 수 있으니까."
```

### 2-6. 팀 CONTRACT.md에 "토큰 절약 규칙"도 넣어두기

2편에서 만든 `CONTRACT.md`에 아래처럼 한 줄만 추가해두면, 4명 전원이 처음부터 절약 모드로 루프를 돌리게 됩니다.

```markdown
## 컨텍스트/토큰 규칙
- 각자 루프는 자기 담당 폴더 + /shared 폴더만 참조 (다른 담당자 폴더 전체를 읽지 않기)
- 검증은 통합 테스트가 아니라 해당 모듈의 유닛 테스트로 한정
- 최대 반복 횟수: 4회. 초과 시 멈추고 실패 원인 요약해서 보고
```

## 3. 통합 실패 대응 런북 (Runbook)

2시간마다 통합을 시도했는데 안 맞을 때, 아래 순서대로 처리하세요. 순서를 지키는 게 중요합니다 — 특히 **④번을 건너뛰고 ③번에서 끝내는 게 가장 흔한 실수**입니다 (직전 대화에서 나온 바로 그 문제입니다).

### ① 증상 진단: 정확히 뭐가 다른지 확인

"안 된다"에서 멈추지 말고, 정확히 어느 파일의 어느 부분이 계약과 다른지 찾아냅니다.

```
지금 통합 브랜치에서 [에러 내용]이 발생해.
backend, frontend 코드와 CONTRACT.md를 비교해서, 정확히 어느 파일의 어떤 부분이
계약과 다른지 표로 정리해줘. 추측하지 말고 실제로 grep/코드 확인해서 알려줘.
```

### ② 원인 분류: 계약이 애매했나, 담당자가 안 지켰나

- **계약이 애매해서 각자 다르게 해석한 경우** → `CONTRACT.md`를 더 구체적으로 고쳐야 함 (예: "응답 형식" → "정확히 `{success, data, error}` 세 필드, 순서까지 명시")
- **계약은 명확했는데 담당자 루프가 안 지킨 경우** → 코드만 고치면 되고, 계약 문서 자체는 안 바꿔도 됨

이 구분이 중요한 이유: 계약이 애매했던 거라면 **다른 팀원도 같은 실수를 이미 했거나 곧 할 가능성**이 높습니다. 이 경우 전체 공지가 필요합니다.

### ③ 통합 브랜치에서 임시로 고쳐서 통합 자체는 통과시키기

지금 당장 데모가 돌아가는지 확인하기 위해 통합 브랜치에서 빠르게 고칩니다. **여기서 끝내면 안 됩니다.**

### ④ 고친 내용을 원래 담당자 브랜치로 반드시 되돌리기 (가장 중요!)

```bash
# 통합 브랜치에서 고친 커밋을 확인
git log --oneline -5

# 그 커밋을 원래 담당자의 워크트리로 옮기기
cd ../team-backend
git cherry-pick <통합 브랜치에서 고친 커밋 해시>
```

이렇게 해야 담당자의 다음 루프 반복이 **고쳐진 상태를 기준으로** 이어서 작업합니다. 이걸 안 하면 2장 도입부에서 말한 "다음 통합 때 또 같은 문제 재발" 상황이 그대로 벌어집니다.

### ⑤ PLAN.md도 같이 확인

담당자의 `PLAN.md`에 옛날 계약 기준으로 적힌 설명이 남아있는지 확인하고, 있다면 같이 고칩니다. 안 그러면 루프가 "계획서엔 이렇게 써있는데 코드가 다르네?"라며 방금 고친 걸 되돌릴 수 있습니다.

```
방금 CONTRACT.md와 코드를 [무엇을 어떻게] 수정했어.
이 담당자의 PLAN.md를 확인해서, 옛날 계약 기준으로 적힌 설명이 있으면
새 계약에 맞게 고쳐줘. 이미 끝난 작업 목록은 건드리지 말고, 설명 텍스트만 동기화해줘.
```

### ⑥ 애매했던 부분이었다면 팀 전체에 한 줄 공지

"CONTRACT.md에서 OO 규칙을 이렇게 명확히 했음, 각자 확인" 정도로 팀 채팅방에 공유합니다. 다음 반복부터 자동 반영되니 "지금 하던 거 끝나면 한번 봐줘" 정도면 충분합니다.

### ⑦ 다음 통합 주기에 재확인

다음 2시간 통합 때 같은 문제가 또 나오는지 확인합니다. 또 나온다면 ②번 원인 분류가 잘못됐을 가능성이 높으니 다시 짚어보세요.

## 4. 자주 발생하는 통합 실패 패턴

| 증상 | 주로 원인 | 해결 |
|---|---|---|
| 프론트가 백엔드 API를 호출했는데 필드가 없다고 나옴 | 이름 표기 규칙(camelCase vs snake_case 등) 불일치 | CONTRACT.md에 정확한 표기 예시를 못 박기 |
| 로컬에선 되는데 통합하면 포트 충돌 에러 | 각자 워크트리가 같은 포트를 씀 | 워크트리별 포트를 미리 배정(3000, 3001, 3002…) |
| 병합했더니 다른 사람이 작성한 파일이 사라짐/깨짐 | 서로 폴더 경계를 안 지키고 남의 파일을 수정함 | CONTRACT.md의 "폴더 구조" 규칙 재공지, 병합 전 `git diff`로 남의 폴더 변경 여부 확인 |
| 테스트는 통과하는데 실제로 실행하면 안 됨 | 테스트가 `skip` 처리되어 있거나 가짜로 통과 | skip된 테스트 검색해서 원상복구, "테스트 skip 금지"를 계약에 명시 |
| 루프가 몇 시간째 같은 작업만 반복 중 | 탈출 조건(최대 시도 횟수)을 안 걸어둠 | 즉시 개입해서 중단, 원인 파악 후 최대 시도 횟수 설정해서 재시작 |
| 환경 세팅(라이브러리 버전 등)이 사람마다 달라서 통합하면 에러 | 각자 워크트리의 의존성 버전이 다름 | 처음에 `requirements.txt`/`package.json`을 계약에 포함해서 고정 |

## 5. 통합 담당자용 2시간 주기 체크리스트

매 통합 시점마다 아래를 순서대로 확인하세요.

- [ ] 각 브랜치를 병합했다
- [ ] 병합 후 실제로 실행해서 에러 없이 켜지는지 확인했다
- [ ] 문제가 있다면 위 런북(2장) ①~⑦ 순서대로 처리했다 (③에서 멈추지 않았다)
- [ ] 고친 내용을 각 담당자 브랜치로 반드시 되돌렸다 (cherry-pick/merge)
- [ ] 팀 전체에 변경 사항을 한 줄로 공지했다
- [ ] 다음 통합 시점을 팀원들에게 다시 확인시켰다
- [ ] (선택) 지금까지 API 비용/토큰 소모가 예상 범위인지 슬쩍 확인했다

## 6. 발표 직전 마무리 (2편 "최종 통합 검증"의 심화)

2편에서 "발표 1~2시간 전, 새 기능 추가 금지 + 전체 리허설" 구간을 잡으라고 했었죠. 여기서는 그 안에서 통합 담당자가 구체적으로 뭘 해야 하는지 다룹니다.

### 최종 검증 절차

1. **완전히 깨끗한 환경에서 실행**: 지금까지 켜둔 서버 말고, 처음부터 다시 클론/설치해서 실행되는지 확인 (당일 노트북이 아니라 다른 노트북에서도 되는지가 이상적)
2. **시연 시나리오를 그대로 따라가며 실행**: 발표에서 보여줄 순서 그대로, 처음부터 끝까지
3. **시연 중 실패할 경우의 플랜 B 마련**: 만약 라이브 데모 중 네트워크 문제 등으로 실패하면 보여줄 백업 화면 녹화본/스크린샷을 미리 준비

### 심사 대응 팁

"왜 이런 방식(루프코딩)으로 개발했나요?"라는 질문이 나올 가능성이 높습니다(이 대회 자체가 그 주제니까요). 아래처럼 짧게 답할 수 있게 준비해두세요.

> "저희는 [OO, OO] 파트를 각자 독립적인 워크트리에서 루프로 동시에 개발하고, 공유 계약 문서로 충돌을 미리 막았습니다. 그 결과 [예: 하룻동안 N개 기능을 구현/사람이 직접 짰다면 X시간 걸렸을 걸 Y시간에]..." 처럼 **구체적인 숫자나 비교**가 있으면 설득력이 높아집니다.

## 7. 해커톤이 끝난 뒤

### 팀 회고 (10분이면 충분)

끝나고 바로, 잊기 전에 아래 세 가지만 짧게 남겨두세요.

- 루프코딩이 특히 잘 먹혔던 작업은 무엇이었나 (다음에도 이런 작업엔 적극 활용)
- 통합 과정에서 제일 골치 아팠던 문제와 그 원인 (계약이 부족했나, 역할 분담이 안 좋았나)
- 다음에 팀플/프로젝트할 때 CONTRACT.md에 미리 추가하면 좋을 규칙

### 결과물 정리

- 최종 코드는 정리해서 GitHub 저장소에 README와 함께 올려두기 (무엇을 만들었는지, 어떤 기술로 구현했는지, 루프코딩을 어떻게 활용했는지)
- 발표 자료, 시연 영상/스크린샷을 따로 보관 — 나중에 포트폴리오나 이력서에 "AI 협업 개발 경험"으로 정리할 때 바로 쓸 수 있습니다
- 팀원별 담당 파트를 명확히 기록해두면 나중에 각자 본인 기여를 설명하기 편합니다

## 8. 1~3편 전체 요약 치트시트

| 편 | 핵심 내용 | 한 줄 요약 |
|---|---|---|
| 1편 | 루프코딩 개념 | 목표(종료 조건)를 정해주면 AI가 계획-실행-확인-수정을 스스로 반복 |
| 2편 | 해커톤 팀 적용 | 공유 계약(CONTRACT.md) → git worktree로 격리 → 자주 작게 통합 → 발표 전 최종 검증 |
| 3편 | 통합 트러블슈팅, 토큰 효율 & 마무리 | 문제 생기면 계약만 고치고 끝내지 말고 각 담당자 브랜치로 수정을 되돌려줄 것 + 컨텍스트 범위·테스트 범위·반복 횟수를 좁혀서 토큰을 아낄 것 |

**대회 전체를 관통하는 단 하나의 원칙**: 루프는 디스크를 기준으로 동작하니, 항상 "다음에 이 사람이 읽을 파일들(코드·CONTRACT.md·PLAN.md)이 이미 정답 상태인가?"만 확인하면 됩니다.

3부작 여기서 마무리합니다. 9/18 대회 화이팅입니다!
