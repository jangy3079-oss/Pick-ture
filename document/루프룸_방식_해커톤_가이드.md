# 루프룸 방식 해커톤 대응 가이드

원 펀치 랄프톤 in Busan 시즌2 — 변경된 대회 규칙 반영판 (2026.9.18)

## 1. 새로 확정된 대회 제약과 이 문서의 가정

오늘(9/18) 대회 도중 규칙이 다음 4가지로 확정됐습니다.

1. 노트북 한 대만 루프코딩을 진행한다.
2. 2시간 동안 루프를 돌리고, 그 노트북을 루프룸에 넣는다.
3. 다른 참가자들은 루프룸 밖에서 그 노트북의 화면공유만 지켜본다.
4. 도중에 사람이 개입해야 하는 상황이 생기면, 들어가서 개입한 뒤 팀 점수 -1점.

이 규칙은 사실 Ralph 루프 기법의 원래 취지 — "사람 개입 없이 스스로 계획-실행-확인-수정을 반복한다" — 를 그대로 채점 기준으로 만든 것입니다. 그래서 기존 가이드의 핵심 기법들(명확한 종료 조건, 스스로 확인하는 수단, 탈출 조건, CONTRACT.md, 토큰 관리)은 버리는 게 아니라 오히려 더 엄격하게 지켜야 합니다 — 이제는 그게 곧 감점을 막는 유일한 방법이기 때문입니다.

**확정된 세부 규칙 (진행요원 확인 완료)**

- 노트북 충전기를 연결하거나 화면이 꺼져서 다시 켜는 경우를 제외하면, 방에 들어가는 모든 행위가 -1점입니다. 사이클이 자연스럽게 끝난 뒤에 들어가는 것도 예외가 아닙니다.
- 개발은 처음 루프를 시작하고 2시간이 지나면 그걸로 완전히 끝입니다. 반복되는 사이클이 아니라 단 한 번의 기회입니다. 이 시점 이후로는 코드를 더 손대지 않고 시연·발표 준비로 넘어갑니다.

이 두 가지 때문에 "2시간마다 반복 통합", "사이클 종료 후 재입장은 무료" 같은 내용은 전부 틀렸던 것으로 확인됐습니다. 아래 모든 섹션은 이 확정 규칙을 기준으로 다시 정리했습니다. 다만 2시간이 끝난 뒤 노트북을 시연 장소로 꺼내오기 위한 입장까지 정말 무료인지는 아직 불명확하니, 이 부분만 진행요원에게 한 번 더 확인하는 걸 추천합니다.

## 2. 팀 역할 재구성

노트북이 한 대뿐이므로, 4명이 각자 노트북을 들고 병렬 개발하던 기존 모델(4인 각자 worktree)은 더 이상 쓸 수 없습니다. 역할을 "노트북을 다루는 사람"과 "지켜보는 사람"으로 다시 나눗니다.

| 역할 | 담당 | 하는 일 |
| --- | --- | --- |
| 오퍼레이터 | 장연수 (노트북 소유자) | 개발 시작 전 사전점검(3장) 마무리 → 노트북을 방에 두고 나옴 → 이후 2시간 동안 원칙적으로 재입장 안 함(충전·화면 꺼짐 제외) → 2시간이 끝나면 개발은 그걸로 종료, 코드를 더 고치지 않고 노트북을 회수해 시연 준비로 전환 |
| 관찰조 3인 (지수·유리·정경) | 화면공유로 실시간 관찰 | 진행상황·에러 메모, 5장 기준으로 "지금 들어갈 가치가 있는가"만 판단해서 오퍼레이터에게 전달(대신 조작하지 않음), 동시에 발표자료·시연 시나리오 준비(코드 관련 후속 계획은 세우지 않음 — 다음 사이클이 없으므로) |

핵심 원칙: 노트북을 물리적으로 만지는 사람은 오퍼레이터 한 명뿐입니다. 관찰조가 "이렇게 고치면 안 될까"를 대신 타이핑하거나 원격 조작하는 건 그 자체가 개입으로 보일 수 있으니, 개입 여부에 대한 합의만 하고 실행은 오퍼레이터에게 전달하는 식으로 운영하세요. 그리고 이번엔 재입장 기회 자체가 사실상 없으므로(충전·화면 꺼짐 제외), 관찰조의 대기 시간은 "다음 사이클 준비"가 아니라 지금 상태 그대로 시연할 수 있도록 발표자료·리허설을 준비하는 시간입니다.

## 3. 루프룸에 넣기 전 사전 준비 체크리스트

방 안에서는 아무도 고쳐줄 수 없으므로, 이전까지 "사람이 어찌든 옵제 보면서 고치면 된다"는 안전망이 사라졌습니다. 탈출 조건과 자체 검증 수단이 이제 유일한 안전장치입니다. 노트북을 방에 넣기 전, 아래를 모두 끝냈는지 확인하세요.

- [ ] `CONTRACT.md` 최신화: API 응답 형식, 이름 규칙, 폴더 구조, "하지 말 것" 목록 — 두 에이전트(예: 인물사진 모델 담당 / 일반사진 모델·백엔드 담당)이 경계를 침범하지 않도록 명확히
- [ ] 각 에이전트별 `PLAN.md`에 이번 2시간에 처리할 작업 목록 + 우선순위 명시 (높은 우선순위부터 실패해도 방이 열렸을 때 가장 가치 있는 것이 끝나게)
- [ ] **탈출 조건을 "사람 호출"이 아니라 "다음 작업으로 자동 이동"으로 설계**: 예를 들어 "4회 연속 실패하면 그 작업은 실패로 표시하고 PLAN.md의 다음 항목으로 넘어가라, 멈춰서 기다리지 말라"처럼. 멈춰서 기다리게 만들면 2시간 내내 아무것도 안 하는 녹으로 남아 있을 수 있고, 이게 결국 개입 유혹을 높입니다
- [ ] 각 에이전트의 검증 범위를 좁은 유닛테스트로 미리 좁혀놓기 (무거운 e2e가 아니라) — 판단 기준 자체가 사람 없이도 명확해야 함
- [ ] `git worktree` 2개로 물리적 분리 + 포트 번호 사전 배정 (포트 충돌은 무인 상황에서 가장 흔한 "누군가 들어가야 하는" 사고)
- [ ] `git stash` 금지, 자동으로 자주 커밋하는 설정/습관 확인 (커밋이 없으면 방 열었을 때 진행 상황을 파악할 방법이 없음)
- [ ] 화면공유가 정상 작동하는지, 관찰조가 있는 곳에서 잘 보이는지 방 밖으로 나가기 전에 미리 테스트
- [ ] 이번 사이클에 외달 외부 API(있다면 키/토큰 만료, 네트워크 장애 등)을 의존하는 작업이 있다면, 그 실패가 "사람 개입이 아니면 해결 불가"한 것인지 미리 판단해두기 (이런 작업은 이번 사이클에 넣지 않는 게 안전)

이번엔 사이클이 한 번뿐이라 되돌릴 기회가 없습니다. 노트북은 100% 충전하거나 처음부터 충전기를 꽂아둔 채 시작하고, 화면 절전·화면보호기를 꺼서 2시간 내내 화면공유가 끊기지 않게 만들어두면, 감점이 면제되는 두 예외 상황(충전 연결, 화면 꺼짐) 자체가 아예 생기지 않게 할 수 있습니다.

## 4. 2시간 루프 사이클 운영 절차

| 단계 | 시점 | 무엇을 하나 |
| --- | --- | --- |
| 전 (방 밖, 약 15분) | 유일한 루프를 시작하기 직전 | 3장 체크리스트 최종 확인 → CONTRACT.md/PLAN.md 커밋 → 화면공유 시작 → 노트북을 방에 두고 문 닫기 |
| 중 (2시간, 무개입·단 한 번) | 루프가 돌아가는 동안 | 관찰조는 화면공유만 보며 기록, 5장 기준으로 정말 필요할 때만 개입 권고(재입장은 -1점, 되돌릴 기회 없음), 동시에 발표자료·리허설 준비 |
| 후 (2시간 종료 = 개발 종료) | 루프가 끝난 순간부터 | 코드는 그 상태로 확정, 더 이상 고치지 않음 — 통합·병합도 루프 안에서 이미 자동으로 끝나 있어야 함(7장) → 시연을 위해 노트북을 꺼내오는 시점의 감점 여부는 진행요원 확인 필요 |

가장 중요한 변화: 예전 가이드처럼 "사이클이 끝나면 방을 열고 재계획"하는 단계가 없습니다. 2시간 안에 나온 결과가 곳 최종 결과물입니다. 그래서 3장의 사전 준비와 7장의 자동 통합 설계가 이 대회에서 가장 중요한 두 섹션입니다.

## 5. 개입 판단 기준과 -1점 최소화 전략

화면공유로 보면서 "들어가서 고치고 싶다"는 유혹이 가장 클 텐데, 이번엔 "다음 사이클을 기다리면 해결된다"는 선택지 자체가 없습니다. 대신 물어야 할 질문은 하나입니다 — "지금 들어가서 고치면, 남은 시간 안에 그 수정이 시연 가능한 결과로 이어지는가, 아니면 그냥 -1점만 날리는가?"

| 상황 | 개입? | 이유 |
| --- | --- | --- |
| 이름/필드가 살짝 어긋남, 탈출 조건에 걸려 에이전트가 스스로 그 작업을 건너뛰고 다음으로 넘어감 | 아니오 | 이미 설계대로 동작 중. 그 기능만 빠진 채 시연하면 됨 — 다시 고칠 기회는 없음 |
| 노트북이 멈춤/크래쉬, 또는 삭제·과금 결제처럼 되돌릴 수 없는 위험한 명령이 실행될 조말 | 예, 즉시 | -1점보다 시연 자체가 불가능해지는 손실이 훨씬 큼 |
| 핵심 시연 기능이 근본적으로 잘못 설계됐는데, 고치면 살아날 가능성이 높고 종료까지 시간이 충분함(예: 30분 이상) | 예외적으로 개입 고려 | 관찰조 2/3 이상 합의가 있을 때만, 최소 개입으로 |
| 위와 같은 상황인데 종료까지 10분 이내로 남음 | 아니오 | 지금 고쳐도 반영·검증할 시간이 없어 -1점만 확정으로 날리는 셀 |

**판단 프로세스**: 관찰조 3인(지수·유리·정경)이 화면을 보며 합의 → 만장일치(최소 2/3) 일 때만 오퍼레이터에게 "개입 권장" 신호를 보냄 → 최종 판단은 오퍼레이터. 이렇게 하면 한 사람의 순간적인 불안감만으로 감점을 자초하는 일을 막을 수 있습니다.

그리고 만약 정말로 들어가야 한다면 **최소 개입**이 원칙입니다: 땅 필요한 파일 하나만 고치고 바로 나오며, 무엇을 왜 고쳤는지 한 줄로 기록해두면 나중에 발표에서 "이 지점에서만 개입했다"를 설명할 때 근거가 됩니다.

## 6. 토큰/컨텍스트 관리 — 무인 상태에서는 더 엄격하게

기존에는 토큰을 많이 먹으면 사람이 어느 정도 눈치를 보고 멈출 수 있었지만, 이제는 2시간 동안 아무도 개입할 수 없으므로 낭비가 걸러지지 않고 그대로 진행됩니다. 방에 넣기 전에 반드시 아래를 설정해두세요.

- 각 에이전트가 참조할 파일 범위를 명시적으로 제한 (자기 폴더 + `/shared`만, 다른 에이전트 폴더 전체를 읽지 않게)
- 검증은 무거운 통합 테스트(E2E)가 아니라 해당 모듈의 유닛테스트로 한정
- 문서/스키마는 프롬프트에 통째로 붙여넣지 말고, MCP 등으로 필요할 때만 조회하도록
- **최대 반복 횟수를 작업당 명확히 설정** (예: 4~6회), 초과 시 "사람 호출"이 아니라 "실패 기록 후 다음 작업으로 자동 이동"하도록 설계 (3장의 탈출 조건과 동일한 원리)
- 방을 열었을 때 토큰/비용 현황도 간단히 확인해서, 남은 사이클 예산을 조절

CONTRACT.md 마지막에 아래처럼 한 줄 규칙을 추가해두면 두 에이전트 모두 처음부터 절약 모드로 돌아갑니다.

```markdown
## 컸텍스트/토큰 규칙
- 각 에이전트는 자기 담당 폴더 + /shared 폴더만 참조
- 검증은 통합 테스트가 아니라 해당 모듈 유닛테스트로 한정
- 최대 반복 횟수: 4회. 초과 시 멈추지 말고 실패 기록 남기고 다음 작업으로 자동 이동
```

## 7. 통합 트러블슈팅 런북 (노트북 한 대, 에이전트 2개 기준)

이번 대회에선 사람이 방에 들어가서 두 브랜치를 병합하는 절차 자체가 성립하지 않습니다(그것도 진입이라 -1점). 그래서 통합(병합)은 사람이 사이클 후에 처리하는 게 아니라, 2시간 루프 안에 자동화된 마지막 단계로 반드시 포함시켜야 합니다.

1. **PLAN.md 마지막 태스크로 통합을 명시**: 두 에이전트 중 하나(또는 별도 통합 전용 태스크)에게 "남은 시간이 [예: 20분] 이하로 남으면, 두 브랜치를 병합하고 CONTRACT.md와 어긋나는 부분을 스스로 진단해서 고쳐라"를 PLAN.md에 못 박아둔다.
2. **병합 실패도 탈출 조건으로 처리**: 병합이 계속 안 되면 사람을 부르는 대신, "어느 부분에서 왜 안 맞는지 로그로 남기고, 안 맞는 기능은 그대로 둔 채 나머지는 살아있는 상태로 커밋"하도록 명시한다.
3. **CONTRACT.md를 병합 자동화의 유일한 판단 기준으로**: 통합 태스크가 참고할 건 CONTRACT.md뿐이어야 하므로, 3장 사전 준비 단계에서 이 문서를 최대한 구체적으로(정확한 필드명, 순서까지) 써둔야 자동 병합 성공률이 올라간다.
4. **작게, 여러 번 자동 통합**: 루프 안에서 한 번에 몰아서 병합하지 말고, PLAN.md 태스크 사이사이에 "작은 단위로 자주 병합 시도"를 넣어두면 2시간 종료 시점에 몰아서 실패할 위험이 줄어든다.

**자주 발생하는 통합 실패 패턴**

| 증상 | 주된 원인 | 예방/자동화된 해결 |
| --- | --- | --- |
| 필드가 없다는 에러 (camelCase vs snake_case 등) | 이름 표기 불일치 | CONTRACT.md에 정확한 표기 예시를 사전에 못 박기 |
| 포트 충돌 | 두 에이전트가 같은 포트 사용 | worktree별 포트를 사전에 배정, PLAN.md에 명시 |
| 다른 에이전트 파일이 사라짐/깨짐 | 폴더 경계를 안 지킴 | CONTRACT.md 폴더 규칙 + 각 에이전트 PLAN.md에 "자기 폴더 밖 수정 금지" 재명시 |
| 테스트는 통과하는데 실제로 안 됨 | 테스트가 skip 처리됨 | 계약에 "skip 금지" 명시 + 통합 태스크가 skip 여부를 자동 검사하도록 지시 |
| 루프가 같은 작업만 계속 반복 | 탈출 조건이 안 걸려있음 | 6장의 탈출 조건을 처음부터 명확히 설정 — 무인 상태이므로 사후 재설정은 불가능 |

이 표의 예방책은 전부 방에 넣기 전(3장)에 끝내둔야 하는 것들입니다. 루프가 도는 동안이나 끝난 뒤에 고칠 방법은 없다는 전제로 다시 한 번 점검하세요.

## 8. 남은 시간 타임라인 (현재 11:53 기준, 17:00 종료)

주제와 실행 방식(안티그래비티 IDE + Claude Code 에이전트 2개 병렬)은 이미 확정된 상태입니다. 이번엔 절대 시각 대신, "개발 시작(T=0)" 기준 상대 시간으로 정리합니다 — 실제 대회 시작 시각에 맞춰 그대로 밀어서 쓰면 됩니다.

| 시점 | 단계 | 내용 |
| --- | --- | --- |
| 개발 시작 전 | 사전 준비 (자유 시간) | 팀 역할 분담(2장), CONTRACT.md/PLAN.md 작성, 통합 자동화 태스크 설계(7장), 노트북 충전·화면 설정 점검(3장) |
| T = 0 | 유일한 루프 시작 | 노트북을 방에 두고 문 닫음, 화면공유 시작 |
| T = 0 ~ T + 2:00 | 단일 2시간 루프 (무개입 목표) | 관찰조는 화면만 보며 기록, 개입은 5장 기준으로만, 동시에 발표자료·시연 리허설 준비 |
| T + 2:00 | 개발 완전 종료 | 코드는 이 시점 상태로 확정. 이후 어떤 코드 수정도 하지 않음 |
| T + 2:00 이후 남은 시간 전부 | 시연 준비 | 노트북 회수(회수 자체의 감점 여부는 진행요원 확인 필요) → 있는 그대로 리허설 → 발표 |

예전처럼 "남은 시간에 맞춰 사이클을 몇 번 돌릴지" 고민할 필요가 없어졌습니다. 유일한 변수는 하나 — 2시간을 얼마나 무개입으로 버티느냐입니다.

### 마무리 체크리스트

- [ ] 충전 연결·화면 꺼짐을 제외한 모든 진입이 감점이고, 개발이 2시간 뒤 완전히 끝난다는 걸 팀 전체가 동일하게 이해했는가
